# reconcile — 고친 흔적에서 지시문 수정안 뽑기

AI가 낸 결과물을 사용자가 고쳤다면, 그 교정은 지시문 어딘가가 부족하다는 증거다.
이 스킬은 그 증거를 읽어 **다음에 같은 교정이 필요 없게 만드는 가장 작은 지시문 수정**을 찾는다.

교정 하나마다 규칙 하나를 더하는 것이 목표가 아니다. 지시문은 길어질수록 덜 지켜진다.

## 필요한 것

1. **초안** — AI가 처음 낸 결과물
2. **최종본** — 사용자가 실제로 보내거나 확정한 버전
3. (선택) **지시문** — CLAUDE.md, 스킬 문서, 프로젝트 지침, 메모리처럼 초안을 만들 때 영향을 준 문서

같은 대화 안에 초안과 최종본이 둘 다 있으면 그것을 쓴다. 하나라도 없으면 요청하고 멈춘다.
기억으로 복원하지 않는다.

사용자가 직접 고친 글이 없고 "이렇게 바꿔 줘"라는 피드백과 그에 따라 AI가 다시 쓴 글만 있을 수 있다.
이때 근거는 다시 쓴 글이 아니라 **사용자의 피드백 문장**이다. 다시 쓴 글도 AI가 쓴 것이기 때문이다.

## 절차

### 1. 차이를 모은다

두 글을 끝까지 읽은 다음, 바뀐 곳을 `초안 → 최종` 한 줄씩 적는다.
삭제, 추가, 순서 이동, 어조, 형식 변화를 모두 포함한다.

### 2. 되풀이될 차이만 남긴다

차이마다 묻는다. **다음 작업에서도 같은 교정이 필요할까?**

- 남긴다: 구조, 분량, 어조, 결론의 위치, 무엇을 넣고 빼는지처럼 다음에도 나타날 것
- 버린다: 오탈자, 띄어쓰기, 그 글에만 해당하는 사실 수정

여러 차이가 한 가지 원칙을 가리키면 하나로 묶는다. 차이 일곱 개가 원칙 하나인 경우가 흔하다.

### 3. 지시문에서 원인을 찾는다

남은 원칙마다 지시문을 찾아보고, 아래 중 어디에 해당하는지 정한다.

| 상태 | 뜻 |
|---|---|
| 규칙이 없다 | 어느 문서도 이 상황을 다루지 않는다 |
| 있는데 멀다 | 규칙은 맞지만 작업하는 시점에 보이지 않는 곳에 있다 (세션 시작 때만 읽히는 파일 등) |
| 있는데 모호하다 | 너무 넓거나 좁거나 약해서 초안을 바꾸지 못했다 |
| 서로 부딪힌다 | 이번 교정이 기존의 명시적 규칙과 충돌한다 |
| 여러 곳에 복사돼 있다 | 같은 규칙의 사본이 다른 문서에 있어 한 곳만 고치면 나머지가 낡는다 |

규칙끼리 부딪히면 어느 쪽이 우선인지 사용자에게 묻는다. 조용히 한쪽을 고치지 않는다.

지시문을 볼 수 없으면 이 단계를 건너뛴다. 그때는 "규칙이 없다"고 단정하지 말고,
사용자가 자기 지시문에 붙여 넣을 수 있는 문구만 제안한다.

### 4. 가장 작은 수정을 고른다

위에서부터 차례로 묻고, 처음으로 "예"가 나온 곳에서 멈춘다.

**줄인다**
1. 낡았거나 방해가 되는 규칙을 지우면 해결되는가
2. 겹치는 규칙을 하나로 합치면 되는가

**고친다**
3. 맞는 규칙을 작업 시점에 보이는 자리로 옮기면 되는가
4. 모호한 규칙을 고쳐 쓰면 되는가
5. 늘어나는 금지 목록을 기준 하나로 바꿀 수 있는가

**밖으로 뺀다**
6. 지시문이 아니라 코드나 검사로 강제할 수 있는가. 같은 당부가 지시문에 여러 번 나온다면 후보다

**미룬다**
7. 근거가 이번 한 번뿐인가. 그렇다면 보류하고, 다음에 또 나오면 그때 규칙으로 만든다

**늘린다**
8. 위 어느 것도 아닐 때만 규칙을 추가한다. 원칙 하나에 규칙 하나

수정안이 정해지면 **되짚어 본다.**

- 원래 실패 사례를 새 문구에 대입한다. 초안이 달라졌겠는가
- 반대 방향 사례도 대입한다. 최종본이 살려 둔 것까지 막지는 않는가

### 5. 제안하고, 승인받고, 고친다

- 승인받기 전에는 어떤 지시문 파일도 고치지 않는다.
- 제안에는 현재 문구의 인용, 바꿀 문구 전체, 넣을 위치를 적는다. 사용자가 그대로 붙여 넣을 수 있어야 한다.
- 승인되면 그 변경만 적용한다. 같은 규칙의 사본이 다른 문서에 있으면 함께 제안한다.
- 고친 뒤 그 부분을 다시 읽어 위치와 문구를 확인한다. 고치지 못했으면 고쳤다고 말하지 않는다.

## 보고 형식

```
## 결론
의미 있는 차이 N건. 권고는 옮기기 1건 + 고쳐 쓰기 1건. (한 문장)

## 의미 있는 차이
- `초안의 모습` → `최종의 모습` : 이 차이가 보여 주는 것

## 수정 제안
1. [옮기기] 무엇을 어디로
   - 근거: 어떤 차이가 이 수정을 뒷받침하는가
   - 현재 문구: "…"
   - 바꿀 문구: "…"
   - 위치: 파일과 절
   - 되짚기: 원래 사례가 막히는가, 살려야 할 것을 막지 않는가

## 보류·버림
- 항목 : 이유 한 줄

## 승인 요청
고칠 수 있는 지시문이 있으면 적용할지 묻는다. 없으면 붙여 넣을 문구가 최종 산출물이다.
```

두 글이 같으면 "바뀐 곳 없음. 초안이 그대로 쓰였다"고 말하고 끝낸다.
사소한 차이뿐이면 "다음으로 가져갈 것 없음"이라고 말하고 끝낸다.

## 하지 않는 것

- 사용자의 속마음을 추측하지 않는다. 글의 변화가 보여 주는 것만 말한다.
- 최종본이 초안보다 나빠 보이는 변화는 배우지 않는다. 의도한 것인지 묻는다.
- 교정 한 번으로 상시 규칙을 만들지 않는다.
- 승인된 범위를 넘겨 고치지 않는다.
- 초안과 최종본에 개인정보나 고객 정보가 있으면 설명에 필요한 만큼만 인용한다.
- 특정 폴더 구조나 다른 스킬을 요구하지 않는다. 초안과 최종본만 있으면 돌아간다.

## 사례

문서 검증 에이전트가 결과를 채팅으로 보고했는데, 사용자가
"너무 복잡하다. 문제가 있는지 없는지부터 말해 달라"고 했다.

**첫 번째 교정**

- 차이: 등급 집계표 삭제, 결론을 문서별 제목에 단정, 질문 네 개를 한 줄로 압축, 도구 수정 경위 삭제 등 7건
- 묶으면 원칙 하나: 파일 리포트와 채팅 보고는 역할이 다르다
- 원인: 초안이 틀린 것이 아니었다. 스킬 문서가 파일 리포트에 넣으라고 한 내용을 채팅에 그대로 옮긴 것이다.
  스킬 문서는 리포트 작성에서 끝났고, 그 결과를 사람에게 어떻게 말할지는 어디에도 없었다.
  같은 취지의 메모가 있었지만 세션 시작 때만 읽히는 곳에 있었다 (있는데 멀다)
- 수정: 규칙 추가 없이 **옮기기 1건**(보고 규칙을 스킬 문서의 리포트 작성 절 바로 뒤로)과
  **줄이기 1건**(메모를 한 문단으로)

**두 번째 교정**

- 상황: "보고에 넣지 말 것" 목록이 생겼는데, 사용자가 살려 둔 민감도 수치 한 줄까지 그 목록이 막고 있었다
- 수정: 금지 목록을 **"판단을 바꾸는 것만 쓴다"**는 기준 하나로 바꿨다 (고친다 5번)
- 되짚기: 첫 초안의 군더더기 4종은 새 기준에 걸리고, 살려야 할 한 줄은 허용된다
- 부딪힘: 새 판정 어휘가 설계 문서의 "승인 권고를 쓰지 않는다"와 충돌해 사용자에게 물었고,
  적용 범위를 갈라 두 문서에 모두 적었다
